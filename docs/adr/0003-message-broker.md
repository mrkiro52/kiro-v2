# ADR-0003 Выбор брокера сообщений

Дата — 20 ноября 2026.

Статус — Proposed, на ревью.

Задача — [DEV-1](https://github.com/mrkiro52/kiro-v2/issues/5). Локальное окружение — [DEV-2](https://github.com/mrkiro52/kiro-v2/issues/6). Реализация доставки — [DEV-7](https://github.com/mrkiro52/kiro-v2/issues/20).

## Зачем нужен брокер

На первом этапе Auth, Users и Social работают в одном приложении и вызывают друг друга через Python. Выбираем брокер для сценариев, где нужна асинхронная доставка, в том числе при выделении отдельных сервисов. Когда именно подключать брокер к конкретному сценарию, нужно решить отдельно.

В DEV-7 нужно доставлять сообщения после перезапуска потребителя, повторять обработку при временных сбоях и складывать проблемные сообщения в отдельную очередь (DLQ).

## Что сравнили

| Критерий | RabbitMQ | NATS с JetStream |
|---|---|---|
| Доставка при отключённом потребителе | Сообщения ждут в заранее настроенной очереди | Сообщения сохраняются в потоке в пределах его политики хранения |
| Одно событие для нескольких обработчиков | Exchange направляет событие в отдельную очередь каждого обработчика. Экземпляры одного обработчика читают общую очередь | Отдельный consumer для каждого обработчика. Экземпляры одного обработчика могут делить pull consumer |
| Повторы | Есть подтверждения обработки. Задержку и предел повторов нужно настроить | Есть подтверждения и настройки повторной доставки, включая `MaxDeliver` |
| Сообщения после исчерпания попыток | Dead-letter exchange (DLX) направляет сообщение в настроенную DLQ | JetStream останавливает повторную доставку этому consumer и отправляет уведомление. Перенос в DLQ требует дополнительной логики |
| Повторное чтение обработанных сообщений | Для этого есть RabbitMQ Streams | Доступно в пределах настроенной политики хранения |

Core NATS доставляет сообщения активным подписчикам. Для восстановления после простоя потребителя в NATS нужен JetStream. Повторное чтение уже обработанной истории пока не входит в требования DEV-7. Поэтому Kafka с её моделью журнала событий оставляем за рамками текущего выбора.

## Решение

Выбираем **RabbitMQ**. Он позволяет развести события по очередям и направлять сообщения в DLQ средствами брокера. Это упрощает реализацию требований DEV-7 к обработке сбоев.

## Что уточняем в DEV-7

- Настраиваем очереди и маршрутизацию, задержку и предел повторов, DLX и DLQ.
- Для надёжной публикации используем outbox или эквивалент и подтверждения от брокера. Потребитель отправляет `ack` после сохранения результата.
- Обработчики должны выдерживать повторную доставку. Например, повторная обработка `user.registered` не должна создавать второй профиль.
