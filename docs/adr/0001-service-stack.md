# ADR-0001 Стек и структура бэкенда

Дата — 18 ноября 2026.

Статус — Proposed, на ревью.

Задача — [DEV-1](https://github.com/mrkiro52/kiro-v2/issues/5).

## Почему выбираем такой подход

В команде три разработчика, у всех основной язык Python. FastAPI знаком команде лучше Django, поддерживает OpenAPI и подходит для нашего API.

Из двух вариантов - FastAPI и Django + DRF - выбираем FastAPI по опыту команды. У Django есть готовые ORM и админка, а для FastAPI мы выбираем инструменты работы с БД отдельно.

Сейчас делаем Auth, Users и Social. Предлагаем начать с одного приложения, разделённого на модули. Это даст общий запуск и позволит сохранять связанные изменения в одной транзакции. Выделение отдельных сервисов будем планировать по мере необходимости.

## Что выбираем

| Для чего | Инструмент |
|---|---|
| API | Python, FastAPI, Uvicorn |
| Валидация и настройки | Pydantic, pydantic-settings |
| БД и миграции | PostgreSQL, SQLAlchemy 2, Alembic |
| Тесты | pytest, HTTPX |
| Зависимости и проверки кода | uv, Ruff, mypy |
| Запуск | Docker Compose |

Одно приложение содержит модули `auth`, `users` и `social`. Используем одну БД с отдельными PostgreSQL-схемами для таблиц каждого модуля.

## Как организуем код

Исходники лежат в `src/kiro/`, тесты — в `tests/`, миграции — в `migrations/`.

У каждого модуля своя папка внутри `src/kiro/modules/`.

- `router.py` — HTTP-эндпоинты.
- `schemas.py` — Pydantic-схемы запросов и ответов.
- `models.py` — модели таблиц SQLAlchemy.
- `repository.py` — запросы к БД.
- `service.py` — бизнес-логика.

В `main.py` создаём приложение и подключаем роутеры.

Модуль работает со своими таблицами через свои репозитории. Другие модули вызывают его публичные операции, например создание профиля в Users. Внутри приложения это обычные вызовы Python.

Транзакцией управляет выполняемый сценарий. Если регистрация должна сохранить учётные данные и профиль вместе, используем одну сессию и один общий commit. Репозитории выполняют запросы в рамках этой транзакции.

## Основные соглашения

| Область | Договорённость |
|---|---|
| Настройки | Читаем через pydantic-settings. Перечень параметров — в `.env.example`, локальный `.env` добавляем в `.gitignore` |
| Логи | JSON в стандартный вывод. Поля — время, уровень, имя приложения, сообщение и `request_id`. Секреты в логи не пишем |
| `/health` | Возвращает `200`, если приложение работает |
| `/ready` | Проверяет готовность, включая подключение к БД. Возвращает `200` или `503` |
| Ошибки | HTTP-статус и JSON с `code`, `message`, `request_id`. Детали валидации добавляем при необходимости |
| Версия API | Предлагаем `/api/v1`. Несовместимые изменения выносим в следующую major-версию |
| Миграции | Alembic, одна последовательность миграций для приложения |
| Контракты | Сначала согласуем OpenAPI, затем реализуем эндпоинты |

Для ожидаемых ошибок бизнес-логики используем кастомные исключения. Обработчики FastAPI преобразуют их в HTTP-статус и единый формат ответа. Конкретные исключения добавляем вместе с реализацией сценариев.

Точный формат ошибок и схемы API уточняем в DEV-22. Владельца ролей и подробные взаимодействия модулей определяем в DEV-20.

## Что делаем с шаблоном из DEV-1

В `services/_template/` собираем запускаемый каркас FastAPI-приложения с примером модуля, подключением БД, миграцией, логами, базовой трассировкой OpenTelemetry, проверками состояния, тестами и Dockerfile.

В текущем шаблоне Uvicorn пишет стандартные логи в stdout, а OpenTelemetry выводит спаны запросов. Структурированные JSON-логи с `request_id` остаются отдельной доработкой.

Шаблон запускается через `docker compose up`. В README описываем запуск и создание приложения на его основе.

Сейчас используем этот каркас для модульного монолита. Позже его можно использовать для отдельного сервиса. Перенос данных, общих транзакций и взаимодействий при выделении сервиса потребует отдельной работы.
