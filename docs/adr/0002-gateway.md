# ADR-0002 Выбор шлюза

Дата — 18 ноября 2026.

Статус — Proposed, на ревью.

Задача — [DEV-1](https://github.com/mrkiro52/kiro-v2/issues/5). Реализация — [DEV-6](https://github.com/mrkiro52/kiro-v2/issues/19).

Связанное решение — [ADR-0001 Стек и структура бэкенда](0001-service-stack.md).

## Зачем нужен шлюз

На текущем этапе у нас одно FastAPI-приложение с модулями Auth, Users и Social. Перед ним ставим шлюз, который принимает внешние запросы, обеспечивает HTTPS, применяет общие ограничения и направляет запросы в приложение.

Сейчас все продуктовые маршруты ведут в приложение kiro. При выделении отдельных сервисов сможем менять их адреса назначения на шлюзе, сохраняя адреса API и формат запросов для клиента.

## Что сравнили

Рассматриваем открытые версии Traefik Proxy и Kong Gateway OSS.

| Критерий | Traefik Proxy | Kong Gateway OSS |
|---|---|---|
| Маршрутизация | Router выбирает запрос, Service задаёт приложение назначения | Route выбирает запрос, Gateway Service задаёт приложение назначения |
| Конфигурация | Файлы и providers, в том числе Docker labels и обнаружение контейнеров | Декларативный YAML в DB-less-режиме, отдельная БД шлюзу в этом режиме не нужна |
| HTTPS | TLS и автоматизация сертификатов через ACME | TLS и ACME-плагин |
| Проверка JWT | ForwardAuth делегирует проверку нашему Auth. Штатный JWT middleware доступен в платном Hub | Есть JWT-плагин, его ключи и Consumers нужно согласовать с нашим Auth |
| Ограничение запросов | Middleware RateLimit | Плагин Rate Limiting |

Оба варианта подходят для маршрутизации в наше приложение. Выбираем Traefik по удобству интеграции с Docker Compose и возможности использовать обработчик проверки из нашего Auth через ForwardAuth.

## Решение

Используем **Traefik Proxy + ForwardAuth**. Обработчик проверки авторизации размещаем в модуле Auth того же FastAPI-приложения.

Для защищённого запроса порядок работы следующий.

1. Клиент отправляет запрос с access JWT в Traefik.
2. Traefik обращается к внутреннему эндпоинту Auth для проверки токена, например `/internal/auth/verify`.
3. Auth проверяет токен. При успехе возвращает `2xx` и проверенные данные пользователя в согласованных служебных заголовках.
4. Traefik передаёт исходный запрос в kiro с проверенным контекстом пользователя.

При отказе Auth шлюз возвращает его ответ клиенту. При ошибке связи с Auth защищённый запрос отклоняется.

## Как делим ответственность

| Компонент | За что отвечает |
|---|---|
| Traefik | Маршрутизация, HTTPS и редирект с HTTP, общий rate limit, CORS, ограничения размера запроса и настройка заголовков |
| Auth | Выпуск и проверка токенов, правила срока действия и отзыва доступа |
| Users и Social | Проверка прав на конкретные данные и действия, например приватности профиля или изменения поста |

Проверка JWT включает подпись, допустимый алгоритм, срок действия и согласованные значения issuer и audience. Правила блокировки пользователя и отзыва доступа определяем вместе с реализацией Auth и требованиями ИБ.

Публичные маршруты, например вход и регистрация, определяются по контрактам и получают отдельные правила. Защищённые маршруты используют ForwardAuth.

Служебный обработчик проверки доступен шлюзу по внутренней сети. Он исключается из публичной маршрутизации и из проверки через ForwardAuth, чтобы избежать повторного вызова самого себя.

Прямой внешний доступ к FastAPI закрывается. Шлюз очищает присланные клиентом заголовки идентификации и передаёт только согласованные заголовки от Auth, например `X-User-Id`. Приложение доверяет этому контексту на границе со шлюзом.

Для шлюза настраиваем JSON access-логи, метрики Prometheus и трассировку OpenTelemetry в рамках DEV-6.

## Что это даёт и чего стоит

Проверка авторизации подключается единообразно к защищённым маршрутам. Логика проверки остаётся в Python-коде Auth. При появлении отдельных приложений они смогут получать одинаковый проверенный контекст пользователя.

Для каждого защищённого запроса получается дополнительное HTTP-обращение к Auth. Пока Auth находится в монолите, оба обращения приходят в одно FastAPI-приложение, это добавляет задержку.

В будущем можно рассмотреть JWT middleware из Traefik Hub. Перед заменой ForwardAuth нужно сверить правила проверки, особенно блокировку пользователя и отзыв доступа, которые требуют актуального состояния.

## Что уточняем при реализации

- Формат access JWT, алгоритм подписи, ключи, срок действия и правила отзыва.
- Служебный маршрут проверки, формат его ответа и заголовки пользователя.
- Лимиты запросов, таймаут проверки, разрешённые домены CORS и настройку сертификатов.
