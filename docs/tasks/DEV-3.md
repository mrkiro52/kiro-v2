# DEV-3 CI

**Исполнитель:** Бэкендер / DevOps · **Волна:** 2 · **Зависит от:** DEV-2 (#6), SEC-4 (#7)

## Зачем
CI должен собирать и проверять только то, что изменилось, иначе в монорепо сборка станет долгой. Пайплайн — основа для всех сервисов.

## Что нужно на входе
- DEV-2 (структура монорепо), SEC-4 (проверки ИБ)
- DEV-1 (стек, шаблон сервиса)

## Что сделать
1. Настроить GitHub Actions с определением изменённых путей (`paths-filter` или аналог): сервис, фронтенд, админка, контракты, docs.
2. Для сервисов: lint → тесты → сборка Docker-образа → (на main) публикация образа в реестр.
3. Подключить проверки безопасности из SEC-4.
4. Для контрактов: проверка OpenAPI (lint, например Spectral).
5. Настроить кэширование и ограничение времени сборки.
6. Описать, как подключить CI для нового сервиса.

## Что должно получиться
- `.github/workflows/ci.yml` (+ reusable workflows)
- `docs/devops/ci.md`

## Критерии готовности
- [ ] PR, меняющий один сервис, запускает CI только для него.
- [ ] Обязательные проверки включены в защиту `main`.
- [ ] Пайплайн шаблонного сервиса из DEV-1 зелёный.
- [ ] Время типичного PR-пайплайна ≤10 минут.

## С кем согласовать
Platform-лид, ИБ (SEC)

## Вне объёма
Деплой на staging/prod — этап 2.

> Места, помеченные «предложение» или «предложить», — рекомендации аналитика, которые исполнитель должен проверить и подтвердить с владельцем решения.
