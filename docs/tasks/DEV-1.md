# DEV-1 Стек и шаблон сервиса (ADR)

**Команда:** Бэкенд · **Исполнитель:** Бэкендер / архитектор · **Старт:** **сразу**

## Зачем
Все сервисы v2.0 должны строиться одинаково, иначе командам будет трудно поддерживать чужие сервисы. Нужно принять решение по стеку и создать шаблон, от которого стартует каждый новый сервис (в первую очередь Auth).

## Что нужно на входе
- Требования v2.0: PostgreSQL на сервис, Redis, RabbitMQ/NATS, Docker Compose, OpenTelemetry
- `docs/01-context.md`
- Навыки команды: сейчас JS/Node (Express) в v1, часть участников — ML (Python)

## Что сделать
1. Сравнить 2–3 варианта стека бэкенда (например Node.js + Fastify/NestJS, Python + FastAPI, Go) по критериям: навыки команды, скорость старта, поддержка OpenAPI, экосистема.
2. Принять решение и оформить ADR-0001 (стек сервисов) по шаблону.
3. Определить соглашения: структура проекта сервиса, конфигурация через env, логирование (JSON), health/ready эндпоинты, обработка ошибок, версионирование API, миграции БД (инструмент).
4. Определить выбор по Gateway (Traefik/Kong) и брокеру (RabbitMQ/NATS) — либо принять ADR, либо зафиксировать как открытый вопрос с дедлайном.
5. Собрать шаблон сервиса (`services/_template/`): Dockerfile, healthcheck, подключение к PostgreSQL, миграции, заготовка тестов, lint, OpenTelemetry.

## Что должно получиться
- `docs/adr/0001-service-stack.md`
- `docs/adr/0002-gateway.md`, `0003-message-broker.md` (или запись в open questions)
- `services/_template/` с README «как создать новый сервис»

## Критерии готовности
- [ ] ADR принят (статус Accepted) после ревью архитектора и 2 разработчиков.
- [ ] Шаблон запускается командой `docker compose up`, отвечает на `/health`.
- [ ] README шаблона позволяет создать новый сервис за ≤30 минут.
- [ ] Решения по Gateway/брокеру приняты или явно отложены.

## С кем согласовать
Архитектор, Platform-лид, ИБ (SEC)

## Вне объёма
Реализация Auth — это DEV-5. Развёртывание на серверах — этап 2.
