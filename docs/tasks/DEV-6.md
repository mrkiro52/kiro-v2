# DEV-6 Gateway: маршрутизация и проверка токена

**Исполнитель:** Бэкендер / DevOps · **Этап 2 (Фундамент)** · **Зависит от:** DEV-3 (#12), DEV-5 (#18), SA-5 (#17)

## Зачем
Gateway — единая точка входа для фронтенда (`api.` поддомен). Он направляет запросы в сервисы, проверяет токен и ограничивает частоту запросов. Без него фронтенд не сможет работать с сервисами безопасно и одинаково.

## Что нужно на входе
- Решение по Gateway из ADR-0002 (Traefik или Kong), DEV-1
- `contracts/*.openapi.yaml` (SA-5)
- Требования SEC-2 к токенам; прототип Auth (DEV-5)

## Что сделать
1. Развернуть Gateway в локальном `docker-compose` и на staging (по готовности DEV-18).
2. Настроить маршруты `/api/auth/*`, `/api/users/*`, `/api/social/*` на сервисы согласно контрактам.
3. Настроить проверку access-токена (JWT/introspection) и передачу `user_id` и роли в сервисы заголовками; запретить подмену этих заголовков клиентом.
4. Настроить rate limit, CORS (только разрешённые домены), ограничение размера тела запроса, security-заголовки.
5. Настроить TLS на staging (сертификаты), редирект HTTP→HTTPS.
6. Добавить access-логи в JSON, метрики Prometheus, трассировку (OpenTelemetry).
7. Написать README: как добавить маршрут для нового сервиса.

## Что должно получиться
- Конфигурация Gateway в `infra/gateway/`
- Обновлённый `docker-compose.yml`
- `docs/devops/gateway.md`

## Критерии готовности
- [ ] Запрос без токена к защищённому маршруту получает 401, с токеном — доходит до сервиса.
- [ ] Клиентские заголовки `X-User-Id` и подобные игнорируются и перезаписываются.
- [ ] Превышение лимита возвращает 429.
- [ ] Метрики и логи видны в мониторинге.

## С кем согласовать
Архитектор, ИБ (SEC), Platform-лид

## Вне объёма
Выпуск токенов — это Auth (DEV-8). Продакшен-деплой — отдельный этап.
