# SEC-7 Проверить open-source сканеры на работоспособность

**Команда:** ИБ · **Исполнитель:** Специалисты ИБ (вместе с Lead AppSec) · **Старт:** **сразу**

## Зачем
В SEC-0 предложен набор open-source инструментов для SSDLC. Прежде чем встраивать их в CI, нужно убедиться, что они реально работают: ставятся, находят уязвимости на контрольных примерах, не тонут в ложных срабатываниях и не требуют платных функций. Процесс — [SSDLC KIRO v2](../security/ssdlc.md), раздел 6.

## Что нужно на входе
- SEC-0 и `docs/security/ssdlc.md` (раздел 6 «Инструменты»)
- Кандидаты: Opengrep (SAST), Trivy (SCA, образы, IaC, секреты, SBOM), ORT (OSA, лицензии), ZAP (DAST), Gitleaks (секреты), DefectDojo Community (ASOC), Dependency-Track (SBOM после релиза)

## Параллельные входы (не блокируют)
- DEV-1 (стек) — пока стек не выбран, проверять на популярных стеках-кандидатах (Node.js/TypeScript, Python)

Не ждать: работать по допущениям, сверить, когда результат появится.

## Что сделать
1. Подготовить контрольные проекты: заведомо уязвимые (например, OWASP Juice Shop, NodeGoat, DVWA или свои примеры) и «чистый» пример на стеке-кандидате.
2. Для каждого инструмента: установить локально и в Docker, запустить на контрольных проектах, сохранить отчёт.
3. Оценить: что нашёл из известных уязвимостей, сколько ложных срабатываний, время работы, формат отчёта (SARIF/JSON), работа без интернета/SaaS, лицензия движка и правил.
4. Проверить импорт отчётов в DefectDojo (поднять локально через Docker Compose).
5. Проверить запуск каждого сканера в GitHub Actions на тестовом репозитории (время, кэш баз).
6. Свести результаты в таблицу и дать рекомендацию: брать / брать с ограничениями / заменить.

## Что должно получиться
- `docs/security/scanners-evaluation.md` — таблица по инструментам с выводами
- Конфигурации и команды запуска в `infra/security/` (черновик)

## Критерии готовности
- [ ] Каждый инструмент из списка запущен хотя бы на одном уязвимом и одном чистом проекте
- [ ] Для каждого записаны: найденное, ложные срабатывания, время, лицензия, ограничения
- [ ] Проверен импорт хотя бы двух отчётов в DefectDojo
- [ ] Рекомендация обсуждена с Lead AppSec и учтена в ADR SEC-0

## С кем согласовать
Lead AppSec / DevSecOps

## Вне объёма
Встраивание в CI проекта — SEC-4; DAST на staging — SEC-9.

> Места, помеченные «предложение» или «предложить», — рекомендации, которые исполнитель проверяет и подтверждает с владельцем решения.
