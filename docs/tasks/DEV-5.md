# DEV-5 Прототип сервиса Auth

**Исполнитель:** Бэкендер · **Волна:** 5 · **Зависит от:** SA-5 (#17), DEV-1 (#5), DEV-3 (#12)

## Зачем
Первый настоящий сервис v2.0: проверка выбранного стека, шаблона, CI и контрактов на практике. Прототип — не прод, но должен соответствовать контракту.

## Что нужно на входе
- `contracts/auth.openapi.yaml` (SA-5)
- ADR-0001 и `services/_template/` (DEV-1)
- CI (DEV-3), требования SEC-2
- Схема БД Auth (SA-4)

## Что сделать
1. Создать `services/auth/` из шаблона сервиса.
2. Реализовать миграции БД по схеме SA-4.
3. Реализовать эндпоинты регистрации и входа (минимум) по контракту; остальные — по возможности.
4. Реализовать требования SEC-2: хэширование, токены, rate limit, логирование.
5. Публиковать события (`user.registered`) в брокер.
6. Написать тесты (юнит + интеграционные), включая негативные сценарии; проверить контракт тестами (Schemathesis/Dredd или аналог).
7. Подключить к CI и запустить в docker-compose; описать запуск в README сервиса.

## Что должно получиться
- `services/auth/` с кодом, тестами, Dockerfile, README
- Зелёный CI
- Короткая демонстрация (запись/скрипт) регистрации и входа

## Критерии готовности
- [ ] Регистрация и вход работают в локальном окружении.
- [ ] Реализация соответствует OpenAPI (контрактные тесты зелёные).
- [ ] Реализованы обязательные требования SEC-2; отклонения записаны.
- [ ] ИБ провёл ревью кода; замечания закрыты или заведены задачами.

## С кем согласовать
Архитектор, ИБ (SEC), Системный аналитик

## Вне объёма
Подтверждение email, OAuth, 2FA, продакшен-деплой — вне объёма прототипа.

> Места, помеченные «предложение» или «предложить», — рекомендации аналитика, которые исполнитель должен проверить и подтвердить с владельцем решения.
