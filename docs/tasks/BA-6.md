# BA-6 Глоссарий и доменная модель

**Команда:** Бизнес-аналитика · **Исполнитель:** Бизнес-аналитик · **Старт:** **сразу**

## Зачем
Команды из разных областей должны одинаково понимать термины («пользователь», «студент», «поток»). Доменная модель — основа для границ сервисов и схем БД.

## Что нужно на входе
- Объём спринта 1 (`docs/04-sprint-1-backlog.md`): регистрация, вход, профиль, посты, комментарии, ответы, лайки, лента
- `docs/01-context.md` — модель Program → Cohort → Enrollment
- `backend/src/db.js` v1 — как сейчас называются сущности
- Результаты BA-1…BA-3 — дополнять глоссарий по мере их готовности

## Параллельные входы (не блокируют)
- BA-1 (#2)
- BA-2 (#3)
- BA-3 (#4)

Эти результаты делаются параллельно, часто другими командами. **Не жди их**: работай по объёму спринта и общим практикам, допущения запиши в своём документе. Когда результат появится — сверь и поправь (обычно это небольшие правки).

## Что сделать
1. Собрать глоссарий: термины, определения, синонимы (на русском и английский идентификатор в коде).
2. Построить доменную модель MVP: User, Credential, Session, Profile, Post, Comment, Like, Report (жалоба); связи и кардинальности.
3. Показать, как модель будет расширяться: Cohort, Enrollment (только как точки расширения, без детализации).
4. Отметить агрегаты и владельцев данных (кто источник правды для каждой сущности).
5. Сверить термины с BA-документами и поправить расхождения.

## Что должно получиться
- `docs/domain/glossary.md`
- `docs/domain/domain-model.md` с диаграммой (Mermaid ER/class)

## Критерии готовности
- [ ] Каждый термин из историй есть в глоссарии.
- [ ] Для каждой сущности указан владелец (сервис-кандидат).
- [ ] Нет двух разных названий одной и той же сущности в документах.
- [ ] Архитектор и BA подтвердили модель.
