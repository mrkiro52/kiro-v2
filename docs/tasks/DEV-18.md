# DEV-18 Staging: деплой, CD, мониторинг и логи

**Команда:** Бэкенд · **Исполнитель:** DevOps / бэкендер · **Старт:** после DEV-3 (#12), DEV-2 (#6)

## Зачем
Без общего стенда нельзя проверять работу сервисов вместе. Нужны автоматический деплой, мониторинг и логи.

## Что нужно на входе
- Серверы reg.ru (этап 0, `docs/03-project-setup.md`)
- CI (DEV-3), Gateway (DEV-6)
- Environments `staging` в GitHub

## Параллельные входы (не блокируют)
- SEC-6 (#36)

Эти результаты делаются параллельно, часто другими командами. **Не жди их**: работай по объёму спринта и общим практикам, допущения запиши в своём документе. Когда результат появится — сверь и поправь (обычно это небольшие правки).

## Что сделать
1. Подготовить staging-сервер: Docker, пользователь для деплоя, SSH по ключам, файрвол.
2. Настроить CD: по merge в `main` собирать образы и обновлять только изменённые сервисы на staging через Environment `staging` и его секреты.
3. Поднять PostgreSQL (отдельные БД и пользователи на сервис), Redis, брокер.
4. Поднять Prometheus, Grafana, Loki, OpenTelemetry collector; дашборды: доступность, ошибки, задержки.
5. Настроить алерты (минимум: сервис недоступен, рост 5xx) и бэкапы БД.
6. Описать процесс отката и runbook.

## Что должно получиться
- `infra/staging/`, workflow деплоя
- Дашборды Grafana
- `docs/devops/staging.md`, `docs/devops/runbook.md`

## Критерии готовности
- [ ] Merge в `main` автоматически обновляет staging.
- [ ] Доступны логи и метрики каждого сервиса.
- [ ] Бэкап БД восстанавливается (проверено).
- [ ] Секреты хранятся только в Environments, не в репозитории.
