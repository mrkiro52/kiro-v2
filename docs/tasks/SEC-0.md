# SEC-0 Организация SSDLC KIRO v2

**Команда:** ИБ · **Исполнитель:** Lead AppSec / DevSecOps · **Старт:** **сразу**

## Зачем
Определить полный цикл безопасной разработки KIRO v2: от требований и проектирования до выпуска, эксплуатации, инцидентов и вывода сервисов. Принцип Shift Left — включать ИБ и автоматические проверки как можно раньше. SEC-1…SEC-6 становятся частями общего процесса.

Проект процесса: [SSDLC KIRO v2](../security/ssdlc.md). Основа — OWASP SAMM, требования — ASVS, сценарии проверки — WSTG; практики защиты поставки и реагирования дополнены из NIST SSDF.

**Подтверждённые роли:** остаточный риск принимает Lead продукта — KIRO; владелец процесса и координатор инцидентов — Lead AppSec / DevSecOps.

## Что нужно на входе
- Контекст проекта и объём MVP: `docs/01-context.md`, `docs/04-sprint-1-backlog.md`
- Текущие задачи ИБ SEC-1…SEC-6
- GitHub Actions, Docker Compose, планируемые сервисы Auth / Users / Social, фронтенд и админка

## Параллельные входы (не блокируют)
- DEV-1 — выбор стека; DEV-3 — общий CI; DEV-18 — staging; DEV-22 — OpenAPI
- SEC-1…SEC-3 — угрозы и требования; SEC-6 — доступы и секреты

Начать по текущей архитектуре, допущения записать. По мере готовности стека и окружения уточнить настройки. Подготовку DAST начать сразу, запуск на приложении — после появления рабочего стенда.

## Что сделать
1. Согласовать процесс: планирование → требования и угрозы → разработка → PR и сборка → staging → допуск и выпуск → эксплуатация → реагирование и улучшения → вывод из эксплуатации. Для этапов определить ответственных, результаты и условия перехода. Связать с SEC-1…SEC-6, DEV и QA.
2. Выбрать и проверить open-source инструменты. Стартовое предложение:
   - **SAST — [Opengrep](https://github.com/opengrep/opengrep):** поиск ошибок безопасности в коде сервисов, фронтенда и админки.
   - **SCA — [Trivy](https://github.com/aquasecurity/trivy):** уязвимости зависимостей и Docker-образов; формирование SBOM — перечня компонентов сборки.
   - **OSA — [ORT](https://github.com/oss-review-toolkit/ort):** состав open-source зависимостей и соблюдение правил использования лицензий. Здесь OSA означает Open Source Analysis.
   - **DAST — [ZAP](https://www.zaproxy.org/docs/automate/automation-framework/):** проверка работающих API и веб-приложения на staging, включая вход под тестовым пользователем.
   - **ASOC — [DefectDojo Community](https://github.com/DefectDojo/django-DefectDojo) + GitHub Actions:** единый учёт находок, повторный импорт без дублей, назначение владельцев и контроль исправлений. ASOC — управление проверками и результатами, а не отдельный сканер.
   - Дополнительно: поиск секретов и проверка Docker/IaC-конфигураций; для SBOM-мониторинга после релиза — [Dependency-Track](https://docs.dependencytrack.org/).
3. Проверить поддержку выбранного в DEV-1 стека, лицензии движков, правил и источников данных, актуальность поддержки и возможность работы без обязательных платных функций. На контрольных примерах проверить полезные и ложные срабатывания. Выбор и ограничения записать в ADR.
4. Согласовать с SEC-4 внедрение в GitHub Actions: быстрые проверки на PR, полные — по расписанию, сканирование образов — после сборки. Проверять изменённые сервисы; при изменении общих зависимостей и правил расширять охват. Сохранить ориентир DEV-3: типичный PR-пайплайн до 10 минут.
5. Подготовить план DAST для Auth / Users / Social: OpenAPI-контракты, тестовые роли, проверка успешного входа, допустимые маршруты и нагрузка. Связать с ручной проверкой SEC-5 и негативными тестами QA-1. Активные проверки выполнять на тестовых данных и стенде, отдельно от production.
6. Определить правила обработки находок: кто разбирает, кто исправляет, сроки, что блокирует PR и как оформить временное исключение. Сначала настроить правила на пилоте, затем блокировать новые достоверные High/Critical и утечки секретов. Ошибку сканера не считать успешной проверкой.
7. Описать необходимые доработки: свои правила Opengrep, сценарии авторизации ZAP, политики лицензий ORT, адаптеры отчётов в DefectDojo. Начать с конфигураций и интеграций; форк движка — только при подтверждённом ограничении, с оценкой трудоёмкости и владельцем поддержки.
8. Определить допуск в production: проверенная версия и SBOM, результаты тестов, действующие исключения, безопасный деплой и восстановление. Дополнить план мониторингом новых уязвимостей, обработкой инцидентов и выводом сервисов.
9. Учесть аккаунты, посты, прогресс и участие в курсах; миграцию данных, роли и админку, будущие AI/ML и Code Runner. Зафиксировать открытые вопросы и завести недостающие задачи. Работа над v1 — вне этого цикла; возможный пентест v1 оформить отдельно.

## Что должно получиться
- `docs/security/ssdlc.md` — согласованный процесс, этапы, инструменты, ответственные, условия выпуска, исправления и реагирование
- ADR в `docs/adr/` — выбор open-source инструментов, ограничения и необходимые доработки
- План уточнения SEC-1…SEC-6, DEV и QA; задачи на DAST, ASOC, OSA/SBOM, безопасный выпуск и реагирование с порядком подключения

## Критерии готовности
- [ ] Описан весь цикл; первый охват — Auth / Users / Social, Gateway, фронтенд, админка и Docker-образы. Для будущих сервисов определён порядок подключения.
- [ ] Для SAST, DAST, SCA, OSA и ASOC выбраны инструменты, проверены лицензии и записаны ограничения.
- [ ] На контрольных примерах подтверждена работа выбранных сканеров; для DAST подготовлен воспроизводимый тестовый запуск.
- [ ] Для каждого этапа внедрения есть задача, ответственный и проверяемый результат; реализация CI остаётся в SEC-4.
- [ ] Определены блокировки PR, условия выпуска, сроки исправления, исключения и порядок реагирования; KIRO принимает риск, Lead AppSec / DevSecOps координирует инциденты.
- [ ] Открытые решения по данным, ASVS, ролям, S3 и ресурсам имеют владельцев и сроки до затрагиваемого этапа.
- [ ] План согласован с Platform и разработчиками; команда понимает, что делать при срабатывании.

## С кем согласовать
Platform-лид, Архитектор, исполнители SEC-4 и DEV-3; принятие рисков — Продакт-владелец.

## Вне объёма
Полная реализация всех интеграций в рамках одной задачи, написание сканеров с нуля, внешний пентест, SSDLC v1. Модель угроз и требования — SEC-1…SEC-3, CI — SEC-4, ручная проверка MVP — SEC-5, доступы — SEC-6. Завершение SEC-0 означает согласование процесса и задач внедрения, а не готовность всех контролей.

> Перечень инструментов — предложение. Окончательный выбор фиксируется после проверки на стеке проекта.
