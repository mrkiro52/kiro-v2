# SEC-9 DAST: автоматическая проверка API и веба на staging

**Команда:** ИБ · **Исполнитель:** Специалист ИБ · **Старт:** после SEC-7 (#44)

## Зачем
Статический анализ не видит проблемы работающего приложения: авторизацию, сессии, заголовки, ошибки конфигурации. Нужна регулярная DAST-проверка Auth / Users / Social на staging. Процесс — [SSDLC KIRO v2](../security/ssdlc.md), разделы 5.5 и 10.

## Что нужно на входе
- SEC-0, SEC-7 (результат проверки ZAP)
- OpenAPI-контракты (DEV-22) и staging (DEV-18)

## Параллельные входы (не блокируют)
- DEV-22 — контракты для импорта в ZAP
- DEV-18 — staging; до его готовности готовить план и запускать на локальном docker-compose

Не ждать: работать по допущениям, сверить, когда результат появится.

## Что сделать
1. Составить план сканирования ZAP Automation Framework: импорт OpenAPI, тестовые роли (студент, куратор, админ), вход и проверка сохранения сессии.
2. Настроить контроль авторизации: если вход не удался — проверка считается проваленной, а не успешной.
3. Разделить пассивные проверки (на каждый деплой staging) и активные (по расписанию, в согласованное окно), ограничить нагрузку и опасные операции.
4. Встроить запуск в GitHub Actions после деплоя на staging; отчёт сохранять и отправлять в ASOC (SEC-10).
5. Проверить покрытие: какие защищённые маршруты реально просканированы.
6. Описать, как разработчику читать отчёт и что делать с находкой.

## Что должно получиться
- План сканирования в `infra/security/zap/`
- Workflow DAST
- `docs/security/dast.md`

## Критерии готовности
- [ ] DAST запускается автоматически после деплоя на staging
- [ ] Сканирование проходит под тестовыми ролями; провал входа даёт ошибку
- [ ] Отчёт связан с версией сборки и попадает в ASOC
- [ ] Активные проверки не ломают общий стенд
