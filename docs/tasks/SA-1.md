# SA-1 Структура документации и шаблоны

**Исполнитель:** Системный аналитик · **Волна:** 1 · **Зависит от:** — (можно начинать сразу)

## Зачем
Все остальные аналитики и разработчики будут писать документы в `docs/`. Без единой структуры и шаблонов документы получатся разными по формату и их будет невозможно найти. Задача блокирует единообразие всей документации v2.0.

## Что нужно на входе
- `docs/README.md` и `docs/01-context.md` в `kiro-v2`
- Правило из решений v2.0: решения фиксируются в ADR, сначала контракт (OpenAPI), потом код

## Что сделать
1. Предложить дерево каталогов `docs/` (процессы, требования, домен, архитектура, БД, безопасность, ADR, шаблоны).
2. Написать шаблон ADR (контекст, варианты, решение, последствия, статус).
3. Написать шаблон описания сервиса (назначение, владелец-команда, API, события, БД, зависимости, SLA).
4. Написать шаблон описания процесса (актёры, шаги, исключения, схема), шаблон пользовательской истории и шаблон описания события.
5. Описать правила: именование файлов, нумерация ADR, где хранятся схемы (формат Mermaid/PlantUML), как делается ревью документа через PR.
6. Положить шаблоны в `docs/templates/`, обновить `docs/README.md`.

## Что должно получиться
- `docs/templates/adr.md`, `service.md`, `process.md`, `user-story.md`, `event.md`
- `docs/CONTRIBUTING-DOCS.md` — правила ведения документации
- Обновлённый `docs/README.md` с деревом каталогов

## Критерии готовности
- [ ] Шаблоны лежат в `main`, влиты через PR с ревью.
- [ ] Любой участник по README находит, куда класть свой документ.
- [ ] Каждый шаблон содержит пример заполнения или пояснения к полям.
- [ ] Шаблоны приняли в работу остальные аналитики (по одному комментарию «ок» от BA и SA).

## С кем согласовать
Архитектор, Продакт-владелец

## Вне объёма
Содержимое самих документов (процессы, домен и т.д.) — это другие задачи.

> Места, помеченные «предложение» или «предложить», — рекомендации аналитика, которые исполнитель должен проверить и подтвердить с владельцем решения.
